1. VISIÓN GENERAL — ¿QUÉ ES 2.5D?

El juego usa una técnica llamada raycasting, popularizada por Wolfenstein 3D (1992) y Doom (1993). A pesar de que la pantalla muestra una perspectiva tridimensional convincente, el mundo interno es completamente plano: una matriz 2D de celdas que son o bien pared o bien camino.

La ilusión de profundidad se construye lanzando rayos desde la cámara del jugador, uno por cada columna de píxeles de la pantalla. Cuanto más lejos choca un rayo con una pared, más pequeña se dibuja esa columna. Es la misma proyección perspectiva que usa la visión humana.

En términos simples: El truco es simple. Si lanzas 640 rayos (uno por pixel de ancho), y cada rayo te dice a qué distancia chocó con una pared, puedes calcular qué tan alta debe ser esa pared en pantalla: altura = ALTO / distancia. A mayor distancia, menor altura.

2. GENERACIÓN DEL LABERINTO — DFS RECURSIVO

ALGORITMOS

Cada partida genera un laberinto distinto mediante el algoritmo de backtracking recursivo (también llamado "recursive DFS maze carver"). Es el algoritmo más común para laberintos perfectos: tiene exactamente un camino entre cualquier par de celdas, sin bucles ni áreas aisladas.

¿Cómo funciona?

El laberinto se representa en una grilla de tamaño (2·F+1) × (2·C+1): las celdas impares son "habitaciones" y las celdas entre ellas son "muros derribables". Todo empieza como paredes (valor 1), y el algoritmo va abriendo pasos.

flowchart TD
    A(["Inicio\ngrid = todo paredes\npila = 0,0"]) --> B["Tomar tope r, c"]
    B --> C{"Hay vecinos\nno visitados?"}
    C -->|"Si"| D["Elegir vecino\naleatoriamente"]
    D --> E["Derribar muro\nentre r,c y vecino"]
    E --> F["Marcar visitado\nApilar vecino"]
    F --> B
    C -->|"No"| G["Backtrack — pop"]
    G --> H{"Pila\nvacia?"}
    H -->|"No"| B
    H -->|"Si"| I(["Laberinto completo"])
            
while (pila.length > 0) {
    const [r, c] = pila[pila.length - 1];
    const vecinos = dirs
        .map(d => ({ nr: r + d.dr, nc: c + d.dc, ... }))
        .filter(v => v.nr >= 0 && v.nr < filasCeldas && !vis[v.nr][v.nc]);

    if (vecinos.length > 0) {
        const v = vecinos[Math.floor(Math.random() * vecinos.length)];
        grid[r * 2 + 1 + v.dr][c * 2 + 1 + v.dc] = 0; // derriba el muro
        grid[v.nr * 2 + 1][v.nc * 2 + 1] = 0;   // abre la habitación
        vis[v.nr][v.nc] = true;
        pila.push([v.nr, v.nc]);
    } else {
        pila.pop(); // backtrack
    }
}
Profundizando: La implementación usa la versión iterativa con pila explícita en lugar de recursión real, evitando stack overflow en laberintos grandes. La complejidad es O(N) donde N = número de celdas lógicas, ya que cada celda se visita exactamente una vez. El factor 2·F+1 en la grilla es la codificación "de pared entre celdas": cada celda lógica ocupa la posición (2r+1, 2c+1) y sus muros compartidos están en las posiciones intermedias.

Variabilidad por nivel

El tamaño del laberinto es aleatorio en cada partida. Se eligen entre 4–7 filas y 7–11 columnas de celdas lógicas, generando laberintos que van de pequeños y fáciles a grandes y laberínticos:

const CELDAS_F = 4 + Math.floor(Math.random() * 4);  // 4..7
const CELDAS_C = 7 + Math.floor(Math.random() * 5);  // 7..11

3. COLOCACIÓN DE LA SALIDA — BFS

GRAFOS

Una vez generado el laberinto, el juego coloca la puerta de salida (cian pulsante) en el punto más lejano del spawn del jugador. No es una distancia euclidiana sino la distancia real a través de los pasillos del laberinto, calculada con BFS (Breadth-First Search).

const cola = [[1, 1]];
dist[1][1] = 0;
let cabeza = 0;

while (cabeza < cola.length) {
    const [f, c] = cola[cabeza++];   // O(1) sin shift()
    const d = dist[f][c];

    if ((f !== 1 || c !== 1) && laberinto.mapa[f][c].tipo === 'camino' && d > maxDist) {
        maxDist = d;
        salidaF = f; salidaC = c;
    }
    // explorar los 4 vecinos transitables...
}
Detalle de implementación: Se usa un índice cabeza en lugar de cola.shift(). Esto es importante: Array.shift() en JavaScript es O(N) porque mueve todos los elementos. Con un puntero de lectura la cola opera en O(1) por elemento, haciendo la BFS total O(N).

La celda de salida cambia su tipo de 'camino' a 'salida', lo que hace que el sistema de spawn de enemigos e ítems la excluya automáticamente del pool de posiciones válidas.

4. EL MOTOR DE RENDERIZADO — DDA RAYCASTING

MATEMÁTICAS

El corazón del motor es el algoritmo DDA (Digital Differential Analyzer). Para cada columna de píxeles x se lanza un rayo con este ángulo:

anguloRayo = (jugador.angulo - FOV/2) + (x / ANCHO_3D) * FOV

El FOV (campo de visión) es de 60° (π/3 radianes), distribuidos uniformemente entre las 640 columnas.

El algoritmo DDA

DDA traversal avanza el rayo celda por celda de la grilla, siempre saltando a la siguiente intersección de línea de cuadrícula más cercana, sin importar si es vertical u horizontal. Es exacto (sin artefactos de sampling) y muy rápido.

while (!hit) {
    if (sideDistX < sideDistY) {
        sideDistX += deltaDistX;  // avanzar al siguiente borde vertical
        mapX += stepX;
        side = 0;
    } else {
        sideDistY += deltaDistY;  // avanzar al siguiente borde horizontal
        mapY += stepY;
        side = 1;
    }
    if (tipoCelda === 'pared' || tipoCelda === 'salida') hit = true;
}

Distancia perpendicular vs. euclidiana

Usar la distancia euclidiana al punto de impacto provoca el efecto "ojo de pez": las paredes a los lados aparecen más pequeñas de lo que deberían. La solución es usar la distancia perpendicular al plano de la cámara.

Sombreado por distancia y cara

Las paredes se oscurecen según la distancia (fog) y según si la cara impactada es norte/sur vs este/oeste, dando profundidad visual sin necesidad de iluminación real:

const shade = Math.min(0.94, distancia / SHADE_DIVISOR + faceDarken);
r = Math.floor(r * (1 - shade));   // oscurecer según distancia

5. TEXTURAS PROCEDURALES Y BUFFER DE PÍXELES

GRÁFICOS

No hay archivos de imagen. Las tres texturas (muro, techo, suelo) se generan programáticamente al inicio usando un canvas oculto, y sus datos de píxel se extraen de una sola vez con getImageData(). El acceso posterior es un simple índice en un Uint8ClampedArray.

// Una sola lectura al inicio...
const muroTexData = texturaMuro.getContext('2d')
    .getImageData(0, 0, TEX_SIZE, TEX_SIZE).data;

// ...acceso O(1) durante el render, sin llamadas a la API del canvas
const texIdx = (texV * TEX_SIZE + texU) * 4;
buf[i]     = muroTexData[texIdx];     // R
buf[i + 1] = muroTexData[texIdx + 1]; // G
buf[i + 2] = muroTexData[texIdx + 2]; // B

El frame entero se construye escribiendo directamente en el array buf (el buffer de ImageData), y se sube al canvas en una sola llamada a putImageData() al final del render. Esto evita miles de fillRect individuales por frame.

¿Por qué es importante? Cada llamada a la API 2D del canvas tiene overhead. Escribir directamente en el ImageData y hacer un único putImageData por frame es la técnica estándar para pixel pushing eficiente en canvas sin WebGL.

Coordenada de textura (u)

Al impactar una pared, se calcula en qué fracción horizontal de la celda ocurrió el impacto. Este valor u (entre 0 y 1) se mapea a la columna de la textura:

let wallX = side === 0
    ? jugador.y + perpDist * dirY   // cara vertical: coordenada Y del impacto
    : jugador.x + perpDist * dirX;  // cara horizontal: coordenada X del impacto
wallX -= Math.floor(wallX);         // fracción decimal = offset dentro del ladrillo

const texU = Math.floor(wallX * TEX_SIZE); // columna en la textura 64px

6. RENDERIZADO DE SPRITES — Z-BUFFER

GRÁFICOS

Los enemigos y los ítems son sprites 2D proyectados en el espacio 3D. El problema central es el orden de dibujado: un sprite detrás de una pared no debe verse, y un sprite más cercano debe tapar a uno más lejano.

El Z-Buffer

Durante el render de paredes, se guarda la distancia perpendicular de cada columna en zBuffer[x]. Cuando se va a dibujar un píxel de sprite en la columna x, solo se dibuja si el sprite está más cerca que la pared registrada:

if (distCorr >= zBuffer[col]) continue; // la pared tapa al sprite

Proyección del sprite

Para saber dónde en pantalla aparece un sprite, se calcula el ángulo entre el jugador y el sprite, relativo a la dirección de visión del jugador:

let deltaAngulo = Math.atan2(dy, dx) - jugador.angulo;
// normalizar a [-π, π]
while (deltaAngulo > Math.PI) deltaAngulo -= 2 * Math.PI;

const xCentro = Math.floor((0.5 + deltaAngulo / FOV) * ANCHO_3D);
const altSprite = Math.floor(ALTO / distCorr);  // más lejos = más pequeño

Personajes sin sprites de imagen

Los enemigos se dibujan coloreando columnas individuales, definiendo zonas anatómicas (cabeza, torso, brazos, piernas, pies) con rangos en la coordenada de textura tc. No hay sprites bitmap, todo es geometría procedural:

const hasHead = Math.abs(col - xCentro) < headRadius;
const hasBody = col >= bodyStartX && col < bodyEndX;
const hasLeg  = (tc > 0.46 && tc < 0.50) || (tc > 0.54 && tc < 0.58);
Orden de dibujado: Los sprites se ordenan de más lejano a más cercano antes de renderizar (painter's algorithm). El Z-buffer resuelve el caso de oclusión por paredes; el ordenamiento previo resuelve la oclusión entre sprites.

Reutilización del caché de rayos

El minimapa necesita dibujar los rayos de visión. En lugar de lanzar todos los rayos dos veces, el render 3D guarda los resultados en rayCache[] y el minimapa los reutiliza directamente, sin costo adicional de cómputo.

7. INTELIGENCIA ARTIFICIAL DE LOS ENEMIGOS

COMPORTAMIENTO

Cada enemigo tiene dos modos de comportamiento que se evalúan cada frame:

ModoCondiciónComportamiento
CazaJugador en rango (<8 celdas) y línea de visión libreSe mueve directamente hacia el jugador a velocidad mayor
PatrullaFuera de rango o sin visibilidadDeambula por pasillos sin retroceder
AtaqueDistancia ≤ 1.2 unidadesInflige daño al jugador en ciclos de cooldown

Línea de visión

Para saber si el enemigo "ve" al jugador, se lanza un rayo lineal entre ambas posiciones y se verifica que no cruce ninguna pared. El muestreo se hace con 10 puntos por unidad de distancia:

function esLineaLibre(x1, y1, x2, y2) {
    const steps = Math.max(Math.ceil(Math.abs(dx) * 10), Math.ceil(Math.abs(dy) * 10), 4);
    for (let i = 1; i < steps; i++) {
        const t = i / steps;
        const cx = Math.floor(x1 + dx * t);
        const cy = Math.floor(y1 + dy * t);
        if (laberinto.mapa[cy][cx].tipo === 'pared') return false;
    }
    return true;
}

Deambulación sin retroceso

En modo patrulla, el enemigo elige la siguiente celda adyacente aleatoriamente, con una restricción: no puede dar media vuelta inmediata. Esto evita que los enemigos vibren en el mismo sitio. Si no hay opciones sin retroceder, se permite la marcha atrás como fallback:

// Excluye la dirección opuesta a la última usada
let candidatos = dirs.filter(d =>
    !(d.dx === -e.lastDx && d.dy === -e.lastDy) && esCeldaValida(d)
);

if (candidatos.length === 0) {
    candidatos = dirs.filter(d => esCeldaValida(d)); // fallback: permite retroceder
}

8. COLISIONES Y MOVIMIENTO — WALL SLIDING

FÍSICA

Una colisión simple "bloquea" al jugador completamente al tocar una pared. Esto se siente torpe porque el jugador no puede deslizarse a lo largo de la pared. La técnica wall sliding resuelve esto probando los ejes X e Y de forma independiente:

// Intenta mover en X solo
if (esCamino(nx + r, y + r) && esCamino(nx - r, y + r) &&
    esCamino(nx + r, y - r) && esCamino(nx - r, y - r)) {
    x = nx;
}
// Intenta mover en Y solo (independiente del resultado anterior)
if (esCamino(x + r, ny + r) && esCamino(x - r, ny + r) &&
    esCamino(x + r, ny - r) && esCamino(x - r, ny - r)) {
    y = ny;
}

El radio del jugador se verifica en las 4 esquinas de su caja de colisión (no solo en su centro), lo que evita que atraviese esquinas de paredes.

9. AUDIO PROCEDURAL — WEB AUDIO API

AUDIO

No hay archivos de audio. Todos los sonidos se sintetizan en tiempo real usando Web Audio API, combinando osciladores con distintas formas de onda y envolventes de amplitud (ADSR simplificado).

Daño recibidoSawtoothFrecuencia baja (120→50Hz), más fuerte — sensación de golpe

function playShoot() {
    const t = audioCtx.currentTime;
    const osc  = audioCtx.createOscillator();
    const gain = audioCtx.createGain();

    osc.type = 'sawtooth';
    osc.frequency.setValueAtTime(180, t);
    osc.frequency.exponentialRampToValueAtTime(60, t + 0.12);
    gain.gain.setValueAtTime(0.25, t);
    gain.gain.exponentialRampToValueAtTime(0.001, t + 0.15);

    osc.connect(gain).connect(audioCtx.destination);
    osc.start(t); osc.stop(t + 0.15);
}
AudioContext y política de autoplay: Los navegadores modernos bloquean el audio hasta que el usuario interactúa con la página. Por eso el AudioContext se crea en la primera acción del usuario (primer disparo, primer movimiento) y si está suspendido se reactiva con audioCtx.resume().

10. EL GAME LOOP

ARQUITECTURA

El motor usa requestAnimationFrame (rAF), el estándar para animaciones en el navegador. rAF sincroniza el loop con la tasa de refresco del monitor (típicamente 60fps) y pausa automáticamente cuando la pestaña no es visible, ahorrando CPU.

flowchart LR
    RAF(["requestAnimationFrame"]) --> T["Decrementar timers\ndisparo · flash · hit · ataque"]
    T --> L["Logica de juego\nmovimiento · IA · pickups · victoria"]
    L --> R["Render\n3D → sprites → mira → HUD → minimapa"]

function buclePrincipal() {
    if (cooldownDisparo > 0) cooldownDisparo--;

    procesarMovimiento();
    actualizarEnemigos();
    verificarPickups();
    verificarVictoria();
    gestionarTemporizador();

    renderizar3D();
    renderizarEnemigos();
    renderizarItems();
    renderizarMira();
    renderizarHUD();
    renderizarMinimapa();

    requestAnimationFrame(buclePrincipal);
}
Timers en frames, no en milisegundos: Valores como COOLDOWN_DISPARO = 22 o MUZZLE_FLASH_DURATION = 4 están en frames, no en milisegundos. Esto significa que a 60fps el flash de disparo dura 4/60 ≈ 66ms. Es una simplificación que funciona bien en hardware típico pero haría los cooldowns más lentos en monitores de 30fps.

11. GESTIÓN DE ESTADO Y TEMPORIZADOR DE BÚSQUEDA

LÓGICA DE JUEGO

La condición de victoria no es matar a todos los enemigos, sino encontrar y pisar la puerta de salida. Matar a todos los enemigos inicia un temporizador de 30 segundos durante el que el jugador debe localizar la salida. Si no lo logra, los enemigos reaparecen.

function gestionarTemporizador() {
    if (nivelCompletado || gameOver) return;

    // Arrancar cuenta atrás cuando el mapa queda sin enemigos
    if (enemigos.length === 0 && !temporizadorActivo) {
        temporizadorActivo = true;
        temporizadorFinMs = performance.now() + TIEMPO_BUSQUEDA_MS;
        return;
    }

    // Hacer reaparecer enemigos cuando expira
    if (temporizadorActivo && performance.now() >= temporizadorFinMs) {
        reaparecerEnemigos(numEnemigosInicial);
        temporizadorActivo = false;
    }
}
performance.now() vs. frames: El temporizador usa performance.now() (tiempo real en milisegundos con alta resolución) en lugar de contar frames. Así los 30 segundos son siempre 30 segundos reales, independientemente de si el juego corre a 60fps o a 30fps.

Spawn seguro con Fisher-Yates

Tanto los enemigos como los ítems aparecen en celdas aleatorias, pero nunca cerca del jugador (mínimo 3 unidades de distancia). El pool de celdas válidas se baraja con Fisher-Yates, el único algoritmo de barajado verdaderamente uniforme en O(N):

for (let i = resultado.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [resultado[i], resultado[j]] = [resultado[j], resultado[i]]; // swap
}
¿Por qué no .sort(() => Math.random() - 0.5)? Ese truco produce distribuciones no uniformes porque el comparador de sort no es transitivo cuando los valores son aleatorios. Fisher-Yates garantiza que cada permutación tiene la misma probabilidad de ocurrir.
